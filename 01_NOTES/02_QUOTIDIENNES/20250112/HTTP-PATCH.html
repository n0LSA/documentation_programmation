    HTTP PATCH

    Analyse du PROMPT et intentions de réponse
    Vous cherchez à comprendre la différence entre la méthode HTTP GET et la méthode HTTP PATCH. Plus précisément, vous voulez savoir ce qu’est une requête PATCH et en quoi elle se distingue d’une requête GET.

    Mon intention est de :

    1. Définir la méthode HTTP GET et son usage courant.
    2. Définir la méthode HTTP PATCH, son concept et sa finalité.
    3. Comparer de manière claire et détaillée les deux méthodes.

    1. La méthode HTTP GET¶

    1.1 Définition¶

    • GET est la méthode HTTP la plus courante, utilisée pour récupérer (lire) des ressources depuis un serveur.
    • Lorsque vous tapez l’URL d’un site web dans votre navigateur, c’est majoritairement une requête GET qui est envoyée pour charger la page.

    1.2 Caractéristiques principales¶

    • Pas de modification du serveur : Une requête GET ne devrait pas modifier ou altérer les données côté serveur. Elle est considérée comme sûre (“safe” en termes HTTP).
    • Pas d’effet de bord : En théorie, un appel GET ne provoque pas d’effets secondaires (pas d’enregistrement en base de données, pas de mise à jour, etc.).
    • Pas de corps de requête : Généralement, les requêtes GET n’ont pas de body (même si techniquement, ce n’est pas interdit, ça n’a pas vraiment de sens dans la pratique).
    • Transfert d’informations : Les paramètres sont souvent passés dans l’URL (query parameters).

    1.3 Exemples concrets¶

    • Afficher la liste de tous les utilisateurs :

      GET /api/users

      Renvoie la liste complète. - Afficher le détail d’un utilisateur :

      GET /api/users/12

      Renvoie la ressource correspondant à l’utilisateur d’ID 12.

    2. La méthode HTTP PATCH¶

    2.1 Définition¶

    • PATCH est une méthode HTTP plus récente (normalisée dans RFC 5789) permettant de mettre à jour partiellement une ressource sur un serveur.

    2.2 Caractéristiques principales¶

    • Mise à jour partielle : Contrairement à PUT qui est censé remplacer la ressource entière, PATCH se concentre sur la mise à jour de certaines parties de la ressource.
    • Utilisation d’un corps de requête : On envoie généralement un body JSON (ou autre format) décrivant les champs à modifier et leurs nouvelles valeurs.
    • Économie de données : Au lieu de renvoyer toute la ressource complète (et risquer d’écraser des champs), on ne précise que les champs à modifier.
    • Non-idempotente ou idempotente : Le caractère idempotent ou non varie en fonction de l’implémentation. En pratique, on considère souvent PATCH comme potentiellement non-idempotente. Par exemple, si vous appelez deux fois de suite un PATCH qui ajoute un élément à un tableau, vous pourriez vous retrouver avec deux ajouts, alors qu’un PUT viserait plutôt à remplacer ou définir une version complète.

    2.3 Exemples concrets¶

    • Mise à jour partielle d’un utilisateur :

      PATCH /api/users/12

      Body JSON :

      {
  "email": "new_email@example.com"
}

      Cela mettrait à jour uniquement le champ email de l’utilisateur d’ID 12, sans toucher aux autres champs.

    • Mise à jour du champ status (comme dans vos précédents exemples) :

      PATCH /api/devices/12/status

      Body JSON :

      {
  "status": true
}

      Ici, on ne met à jour que la colonne status du device 12.

    3. Comparaison entre GET et PATCH¶

    Critère GET PATCH
    Objectif Obtenir (lire) une ressource Mettre à jour partiellement une ressource existante
    Effet côté serveur Ne doit pas modifier la ressource Modifie une (ou plusieurs) partie(s) de la ressource
    Méthode HTTP sûre Oui, considérée comme “safe” et “idempotent” Non, peut générer des modifications en base
    Corps de requête Généralement absent Présent (souvent JSON) décrivant les modifications
    Exemple d’usage Lire une liste, lire un item précis Mettre à jour un champ d’un enregistrement (ex. status)
    Standards Défini dès l’origine du protocole HTTP Standardisé par la RFC 5789 depuis 2010

    4. Qu’est-ce qu’une requête PATCH en résumé ?¶

    • C’est une requête HTTP destinée à mettre à jour uniquement certaines parties d’une ressource existante, au lieu de remplacer la ressource en entier.
    • Elle se distingue de PUT (qui remplace la ressource en entier) et de POST (qui crée une nouvelle ressource).
    • Elle n’a pas pour but de renvoyer du contenu sans modification (contrairement à GET).
    • Dans une API REST, on utilise PATCH lorsqu’on veut modifier un ou plusieurs champs d’un objet tout en conservant les autres champs inchangés.

    Conclusion¶

    • GET : sert à lire des données, n’a pas pour but de les modifier et ne transporte pas (en principe) de body pertinent.
    • PATCH : sert à modifier partiellement une ressource existante, nécessite en général un body JSON décrivant précisément les mises à jour à effectuer.

    Dans le cadre d’une API REST, GET est parfait pour récupérer des informations, tandis que PATCH est recommandé quand vous souhaitez modifier uniquement certaines propriétés d’une ressource sans avoir à envoyer toute la ressource complète, comme dans l’exemple de mise à jour du champ status.
